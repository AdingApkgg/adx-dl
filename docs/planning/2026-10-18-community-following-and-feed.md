# 下一阶段提案：作者关注、更新动态与订阅通知

日期：2026-10-18。状态：**用户于 2026-10-19 批准按此范围实施；开发期间不跑测试，发布前集中验证。**

## 目的与已完成基线

让用户从“找到一首谱面”走到“持续看到喜欢的作者发布新作品或新版本”。作为一次完整任务交付：关注作者、查看更新、按需收到站内提醒、取消关注后停止后续投递，并把恢复和后台运维一起做好。

本提案基于当前源码和已验收的社区平台，而非早期规划文件中的旧进度：三种上传、明确选版发布、数字链接、作者作品、搜索筛选、收藏、举报、预览练习、版本更新说明与差异、谱面评论、论坛订阅、通知、精选、公告、后台已经存在。下一批不重复建设这些能力。现有通知已有全部/未读、按日分组、逐条和当前页标读；这里新增的是作者更新来源和对应偏好。

用户已确定：参考 web 主站；采用持续数小时的完整任务；开发期间不逐次跑测试，准备生产时在构建机集中验证修复。下文的具体默认值是实现建议，不代表用户已确认。预估一个连续 6–10 小时的实现任务，另留集中验证与发布窗口；恢复协议若发现现有格式不兼容，应先调整范围并说明，不能通过减少恢复保障赶工。

## 首版体验

1. 在作者主页及谱面作者区关注作者。匿名点击进入登录，成功后返回原页；自己的主页显示个人管理入口。首次关注只建立关系，不补发旧作品提醒。
2. 登录后在“我的关注”管理作者；点击“关注动态”看到这些作者的新谱面和新公开版本，按发布时间倒序翻页，可直接进入现有预览和下载页面。
3. 每个关注关系提供“接收站内更新提醒”，建议默认关闭。即便关闭提醒，动态仍可浏览；用户主动开启后，未来符合条件的发布进入现有通知中心。
4. 取消关注立即从动态中移除该作者，并停止未投递的提醒；不通知对方。既有通知保留记录，但内容仍受当前公开状态约束。
5. 谱面撤回、下架、作者注销后，动态、通知和旧链接不会继续提供原内容；恢复旧备份也不能使其重新出现。

## 公开与隐私边界

- 关注者名单、本人关注列表、提醒偏好和个人动态都为本人私有；首版不展示粉丝数、公开关注名单，也不向作者暴露关注者身份。
- 公开作者主页仍仅包含现有公开资料和作品。个性化关注状态走私有数据接口，不写入共享 HTML、搜索描述、OG 卡或公共缓存。
- 关注仅允许正常账号关注另一正常账号，不能关注自己；请求采用幂等的“设置为关注/取消”语义，不使用重试会反转状态的 toggle。
- 账号切换、退出、待注销时立即清理本账号缓存、游标和页面数据。所有私有接口和 SSR 响应沿用 private/no-store 与现有跨站请求防护。
- 通知仅使用现有站内渠道；不引入邮件、QQ 私信、浏览器推送或第三方分析平台。

## 什么算一次更新

| 操作 | 动态 | 站内提醒 |
| --- | --- | --- |
| 一首谱面首次明确发布 | 新增一次 | 只发给发布时已关注且开启提醒的人 |
| 作者明确发布此前未公开过的文件版本 | 新增一次 | 满足当前关注、偏好和可见性时投递一次 |
| 修改私有草稿、上传、私有保存 | 不产生 | 不产生 |
| 仅更新简介、标签、署名或版本说明 | 更新现有公开展示，不增加事件 | 不产生 |
| 撤回后重发相同版本、切回已公开过的旧版本 | 不增加事件 | 不产生 |
| 管理员下架后恢复同一公开版本 | 不增加事件 | 不产生 |

“首次”按 `(谱面内部 ID, 文件版本 ID)` 的耐久公开历史判断，不能按当前 publication 是否存在推断。更新事件只有在明确发布成功、对应公开事实越过现有持久化屏障后可见；API 重试、worker 重启、恢复重放都不重新分配事件。

动态窗口建议为最近 90 天，每页 20 条。新关注后可以查看该作者窗口内既有公开更新，这是主动浏览；通知只针对关注/开启提醒之后发生的事件，不补发历史。反复取消再关注视为新的关注期间，之前的待处理事件不补投。

旧数据迁移不伪造历史更新时间：给当前可见 publication 建立一次“上线前作品”基线，只有原本可信的发布时间处于窗口内才显示；不触发通知。以当前版本历史初始化“已公开过”集合，无法从可信历史确认的版本保守记为已见并在迁移报告说明，避免上线时群发。

动态仅显示**当前仍公开且与事件版本一致**的作品；旧事件的版本被新版本替换后从动态中过滤，新版本以自己的事件出现。旧版本通知保留“该版本已更新/不可访问”的状态，可在存在当前公开作品时提供明确的“查看当前版本”入口，不静默把旧版本摘要和新版本下载混在一起。列表、通知 DTO、跳转目标都重新经过同一公开查询，不能从事件快照绕过撤回或注销判断。

## 数据与可靠性方案

复用现有 PostgreSQL、Drizzle、pg-boss、公开事实屏障、通知中心与共享 UI，不新增服务或搬迁前端框架。建议新增私有关系/偏好、公开发布事件和投递幂等记录；表名与模块拆分留给实现者。

- 关系以双方内部账号 ID 唯一，携带关系修订号、关注生效时间和提醒开启时间；公共数字 ID 只用于 URL。并发设置、取消、重新关注必须有明确的新旧关系边界。
- 发布事件从已有明确发布事务产生 outbox；不能从目录抓取、页面访问、updatedAt 或定时扫描猜测。后台分批处理并记录游标，沿用现有 bounded worker 模式，建议每轮最多 20 事件、每事件 100 接收者。
- 事件投递前在事务内重新核对：发布仍有效、双方账号正常、关系修订仍有效、提醒当时和当前均开启。若提醒开启时间晚于事件，则跳过。重复 worker 用 `(事件 ID, 接收者)` 唯一约束去重。
- 同一作者的未读更新建议合为一组，保留最新事件锚点，避免连发淹没直接回复。逐条标读后，迟到的旧事件不得重建同一未读组；新事件可生成新组。排序用事件时间与稳定 ID，而非投递时间。
- 当前通知中心的直接回复、主题订阅、审核结果语义保持原有行为；只增加“作者更新”类型过滤和更新提醒入口，不重新发明整套通知。
- 关注总量建议每账号 500，设置接口按现有账号限流执行；写入错误明确保留原状态。列表只做有索引的有界查询，不全表 fan-out 或一次载入全部关注与作品。

## 备份、恢复与注销必须一起实现

关注关系和偏好属于私有用户控制状态。新增与取消都必须进入仅运维可读的耐久控制记录，取消/关闭提醒先确认持久化再回复成功；不得放入可公开读取的谱面/社区内容事实或截图日志。沿用既有受保护备份存储与校验机制，增加有版本的私有记录类型；写入新类型前先实现拒绝不认识该类型的旧读者和兼容预检。

恢复按现有顺序完成账号删除/撤回等控制事实，再应用关注与偏好的最新修订，最后处理发布事件及通知投递状态。重放优先级为最新修订，删除/取消 tombstone 不因旧数据库覆盖。备份之后已成功的取消关注、关闭提醒和注销不能被恢复抹掉。投递幂等记录、分组水位及已读控制同样覆盖恢复边界；可重建队列，不可把队列重建当成重新发送通知的理由。

恢复无法确认私有控制记录已同步到要求屏障时，先关闭作者动态与更新投递，输出可诊断错误，不能猜测仍然关注或仍然愿意接收通知。已有普通公开浏览不依赖这套新私有状态。

注销立即让涉及该账号的关系、动态和待投递项失效，后台有界清除私有关系；新建账号不继承旧账号关系。运维指标仅返回队列长度、延迟、失败数和屏障状态，不返回关注网络或通知正文。

## 集中验收清单

- 单元/集成：不能自关注、幂等设置、并发取消/重关注、偏好边界、唯一事件、多 worker、迟到事件、每类分页和账号切换。
- 隔离浏览器：作者 A 发布，用户 B 关注但未开启提醒只见动态；开启后新版本收到一次提醒；取消后不再投递；其他账号及匿名看不到 B 的私有数据。沿用完整上传/发布 fixture，不在生产造业务记录。
- 可见性：草稿修改零泄露，元数据更新零新提醒，撤回/下架/注销立即不可访问，同版本重发不群发，旧通知不暴露旧版本摘要。
- 迁移演练：现有用户、谱面数字编号与旧链接不变，历史基线零通知；记录迁移前后数量和回滚兼容限制。
- 故障/恢复：控制日志导出失败、worker 中断、投递重试、恢复到取消/已读之前的备份，均不恢复关系或重复未读；旧读者拒绝新格式。验证恢复演练中的真实私有状态，而非仅比较 SQL 行数。
- 正式流程：`python3 scripts/remote/community-deploy.py` 自动跑真实生产只读无头。增加个人关注、动态、提醒开关页面及后台队列状态读验；生产只读不能替代上述写入/通知投递测试。对应新场景必须纳入强制收据列表，不能只加到可选脚本。
