## 预览与 QQ 的定向排查

公开谱面1第6槽在真实匿名路径连续打开两次正常。旧验收工具将登录态的公开媒体也送入只读桥，再经过生产代理和 SSH 中继；同一1009964字节音频在选中代理20171上30秒没有数据、既有规则代理20172约6.73秒完整返回。登录桥的25秒上游限制触发了音频失败与静音降级，第二轮则在音频尚未完成时触发播放等待超时。

修复严格匹配的公开 maidata/audio/cover 路径，使其按真实 Chromium 公网 HTTPS 和构建机既有代理获取，不携带登录桥密钥或账号 Cookie，每次仍经服务端授权，不缓存媒体；私密页面和 API 继续走受控登录桥。验收容器单独选择生产机已配置的规则代理，配置为当前用户拥有的0600文件；网站 `.env` 和全局代理配置不变。配置与运维约束见 [验收说明](../../apps/community/ops/acceptance/README.md)。

修复后定向验收30310ms通过：匿名两次就绪7130/5576ms，登录态2992/2991ms。四次音频完整200，并实际播放、暂停、拖动；页面与请求错误0、未完成媒体请求0。正式 UI 门禁追加同页两次开关及完整音频检查，避免把静音降级算作音频成功。

QQ 原 NapCat 容器因满盘导致 Docker hosts 文件写入失败而退出；原容器恢复后尚未登录，二维码已过期，且未配置自动登录。使用仅有的原账号快速登录记录恢复，OneBot 随即正常；再用既有接口设置该原账号自动登录，逐字段核对其余配置不变。社区 worker 连续3次确认 reachable/online/good，现有 Redis 健康监控恢复 online。未清除账号数据或重建容器，也没有发送真实验证码/消息。生产视觉检查限制外部挑战请求，登录页的人机验证失败提示属于该只读检查边界；真实验证码送达和第三方再次授权不在这次生产自动验收的通过声明中。
